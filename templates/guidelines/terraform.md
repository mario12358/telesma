# Guidelines: Terraform / OpenTofu

## Style

- `terraform fmt -recursive` (or `tofu fmt -recursive`) on every change; run it, do not argue with it
- Resource and variable names in `snake_case`; the name describes the role, not the type: `resource "aws_s3_bucket" "artifacts"`, not `"artifacts_bucket"` (the type is already in the address); `this` for the single primary resource of a module
- Argument order in a block: `count`/`for_each`, required arguments, optional arguments, nested blocks, `depends_on`, `lifecycle`
- `for_each` over a map/set for collections — indices shift on deletion, keys do not; `count` only as a `0/1` toggle (`count = var.enabled ? 1 : 0`)
- Every variable has `type`, `description`, `nullable = false` by default, a `validation` block where a wrong value is possible, and `sensitive = true` for secrets and anything derived from them
- Every output has `description`; outputs expose ids, ARNs and endpoints, never whole resource objects
- `required_version` and every provider pinned with `~>` to a minor in `versions.tf`; `.terraform.lock.hcl` committed
- Names that depend on project/environment/region are assembled once in `locals` (`name_prefix = "${var.project}-${var.environment}"`) and reused; no string literals repeating the convention
- Comments only for a non-obvious provider constraint (`# the API rejects names longer than 32 characters`)

## Project structure

- One root module per environment as a directory: `envs/dev/`, `envs/staging/`, `envs/prod/`, each with its own `backend.tf` and `terraform.tfvars`; workspaces only for throwaway copies of one environment (preview per PR)
- Reusable code in `modules/<name>/` with `main.tf`, `variables.tf`, `outputs.tf`, `versions.tf`, `README.md` (generated by `terraform-docs`) and `examples/basic/`
- A module does one thing and exposes it fully; a module that wraps a single resource without adding a convention is noise — use the resource directly
- Roots call modules with a pinned `source` (`git::…?ref=v1.4.0` or a registry version constraint), never a floating branch
- `provider` blocks only in root modules; child modules declare `required_providers` and receive providers implicitly or through `providers = {}`
- `backend.tf` per root: remote state (S3 + lock table, GCS, Azure Blob, or a cloud backend) with encryption and versioning on; a local backend only inside `examples/`
- State split by blast radius (network / data / app) so a plan finishes in minutes; cross-root values through `terraform_remote_state` or data-source lookups by tag, never copy-pasted ids
- Resource names in the cloud: `<project>-<environment>-<component>[-<qualifier>]`, lowercase with hyphens, built from `local.name_prefix`; the provider's length limit enforced in a `validation`
- Mandatory tags on every taggable resource via `default_tags` in the provider (AWS) or a `local.common_tags` map merged into every resource: `project`, `environment`, `owner`, `managed_by = "terraform"`, `cost_center`; values from variables, never literals

## Tests

- `terraform validate` and `tflint --recursive` (cloud ruleset enabled in `.tflint.hcl`) run on every PR before any plan; both must be clean
- `terraform test` is the runner: `tests/*.tftest.hcl` next to the module; `run` blocks with `command = plan` for cheap assertions, `command = apply` in an isolated test account for the ones that need real resources
- Assertions check what a caller relies on: output values, computed names, tag presence, the size of a `for_each` set (`condition = length(aws_subnet.private) == 3`)
- Negative tests with `expect_failures = [var.cidr]` prove that a `validation` block rejects bad input
- Every module has `examples/basic/` that `terraform test` applies and destroys in CI; a module without an example is untested
- Plan review is the gate: CI runs `terraform plan -input=false -detailed-exitcode -out=tfplan` and posts the plan on the PR; `apply` runs only after merge, on the same saved plan file — never a fresh plan nobody read
- `trivy config` (or `checkov`) scans HCL in CI: public buckets, `0.0.0.0/0` ingress, unencrypted storage fail the build
- A scheduled `plan` per environment alerts on a non-empty diff (drift)
- Providers are not mocked by hand; `command = plan` runs and `mock_provider` blocks are the only stand-ins

## State and secrets

- State holds secrets in plain text — treat the backend as a secret store: encryption at rest, versioning, access only through the CI role and a break-glass human role; `terraform.tfstate` never in git
- Locking is mandatory; `-lock=false` only inside a documented recovery procedure
- Secrets never in committed `*.tfvars`, `locals` or `default =`: read them with a secret-manager data source (`aws_secretsmanager_secret_version`, `google_secret_manager_secret_version`, `azurerm_key_vault_secret`) or pass `TF_VAR_<name>` from CI's secret store; any tfvars file holding secrets is `.gitignore`d
- Generated credentials come from `random_password` and go straight into a secret-manager resource; they are never plain outputs
- `moved {}` and `import {}` blocks for address refactors, `removed {}` to forget without destroying; `terraform state mv/rm` by hand only when a block cannot express the change
- `lifecycle { prevent_destroy = true }` on stateful resources (databases, data buckets, KMS keys); deleting one requires a code change in the same PR

## What to avoid

- One giant root for everything; a 40-minute plan nobody reads
- `count` over a list of named things — removing one renames and recreates every later one
- Hardcoded account ids, regions, AMI ids and CIDRs — use variables and data sources (`data "aws_caller_identity"`, `data "aws_ami"`)
- `apply -auto-approve` from a laptop; applying a plan that differs from the reviewed one
- Floating module sources (`ref=main`), unpinned providers, an uncommitted lock file
- Secrets in `tfvars`, in `default =`, in outputs without `sensitive`, or printed in CI logs
- Workspaces as the environment mechanism — one wrong `workspace select` away from planning prod with dev variables
- `depends_on` to paper over a missing reference; `ignore_changes = all`; `-target` as routine
- `local-exec`/`remote-exec` provisioners and `null_resource` for configuration management — use the platform's init mechanism or a dedicated tool
- Editing state by hand when `moved`/`removed`/`import` blocks express the change in code

# Guidelines: Ruby (Rails)

## Style

- RuboCop with the project's `.rubocop.yml` (`rubocop-rails`, `rubocop-rspec`, `rubocop-performance` enabled) — run it; do not argue with it. `bundle exec rubocop -a` for safe autocorrect
- 2 spaces, `snake_case` methods/variables, `PascalCase` classes/modules, `SCREAMING_SNAKE` constants; predicate methods end with `?`, raising variants with `!`
- `# frozen_string_literal: true` as the first line of every file
- Keyword arguments for methods with more than two parameters: `def charge(amount:, currency: "EUR")`
- Guard clauses (`return unless order.paid?`) instead of nested `if`; `unless` never with `else`
- Symbols for identifiers and hash keys (`status: :active`), strings for user-visible text
- `Data.define(:amount, :currency)` for small value objects, not a hash with magic keys
- `&.` only when nil is a legitimate value — not to silence a missing-record bug

## Project structure

- Standard Rails layout: `app/models`, `app/controllers`, `app/views`, `app/jobs`, `app/mailers`, `app/services`; Zeitwerk autoloads by path (`app/services/orders/create_order.rb` → `Orders::CreateOrder`) — never `require` app code
- A service object (`app/services/<domain>/<verb_noun>.rb`) when an operation spans more than one model or talks to an external system: constructor with keyword args, one public `call`, returns a result object — not `true`/`false`
- `app/models/concerns/` only for behaviour shared by at least two models; a concern with one includer is a model split in two
- Controllers: authenticate → authorise → load → call → respond, under ~10 lines per action; business logic lives in models and services
- Queries as scopes or class methods (`scope :active, -> { where(status: :active) }`) — never SQL in controllers or views
- Background work in `app/jobs` (Active Job with Solid Queue or Sidekiq); a job receives ids, not objects, and is idempotent
- `Gemfile` with a `~>` constraint per gem, `Gemfile.lock` committed; `bundle exec` in front of every command
- Secrets in `config/credentials.yml.enc` (`bin/rails credentials:edit`), deployment settings via `ENV.fetch("NAME")` — `ENV["NAME"]` silently returns nil

## Tests

- RSpec (`rspec-rails`) is the default; Minitest only when the project already uses it. Never both
- Layout: `spec/models`, `spec/requests` (not `spec/controllers`), `spec/services`, `spec/jobs`, `spec/system` (Capybara), `spec/factories`
- Run one file: `bundle exec rspec spec/services/orders/create_order_spec.rb`; one example: `bundle exec rspec path:LINE`
- FactoryBot: one factory per model with the minimum valid attributes, traits for variants (`create(:order, :paid)`); `build`/`build_stubbed` unless the test needs a row in the database
- Every new endpoint has a request spec: status, response shape and the side effect in the database; negative cases: no session (401/redirect), someone else's record (404), invalid params (422)
- Mock external HTTP with WebMock (`stub_request`), VCR when fixtures are large; never mock ActiveRecord or your own models
- Jobs: `have_enqueued_job` on the caller plus a separate spec for `perform`; mailers: `have_enqueued_mail`
- Time: `travel_to` from `ActiveSupport::Testing::TimeHelpers`, not stubs of `Time.now`
- `shoulda-matchers` for validations/associations; every custom validation also gets an invalid-record example
- Keep `use_transactional_fixtures = true`; parallel runs through `parallelize`, never a shared database between workers

## ActiveRecord and migrations

- Validations in the model AND constraints in the database (`null: false`, `foreign_key: true`, unique index) — a model validation alone does not survive races
- `includes`/`preload` for associations used in a loop; `strict_loading` in development to catch N+1; `find_each` for large tables
- Hash conditions or placeholders (`where(name: value)`, `where("name = ?", value)`) — never interpolation (`where("name = '#{name}'")`), also in `order`, `pluck`, `select`, `joins`; `Arel.sql` only for constant strings
- One schema change per migration, reversible (`change`, or explicit `up`/`down`); `db/schema.rb` committed and regenerated by the migration, never hand-edited
- Adding `NOT NULL` to an existing table: add the column with a default or backfill in a separate step first
- Data migrations are separate from schema migrations and run as a rake task or job, not inside `db:migrate` on large tables
- `after_commit` instead of `after_save` for anything that leaves the transaction (jobs, emails, webhooks); callbacks only for data the model owns — otherwise a service
- `enum :status, { draft: 0, paid: 1 }` with explicit integers; `save!`/`update!`/`create!` in services (raise), non-bang forms only where the return value is checked

## Security

- Strong parameters: `params.require(:order).permit(:title, line_items_attributes: [:sku, :qty])` — never `params.permit!` or `.to_unsafe_h`
- CSRF: `protect_from_forgery with: :exception` stays on for browser controllers; API controllers inherit from `ActionController::API` and authenticate with tokens
- Authorisation on every action (Pundit policy or scoping through the owner: `current_user.orders.find(params[:id])`) — a bare `Order.find(params[:id])` serves other users' records
- `html_safe`/`raw` only on strings built from sanitised parts; prefer `sanitize`, `tag.*` helpers and ERB escaping
- `redirect_to params[:return_to]` only through a whitelist; `allow_other_host: false` by default
- `config/master.key` and `.env` ignored by git; no secret defaults in `config/*.yml`
- Rate limit login, password reset and token endpoints (`rate_limit` in the controller or Rack::Attack)
- `send`/`public_send`/`constantize` never with user-controlled names (`send(params[:action])`)

## What to avoid

- Fat controllers and callback chains that hide side effects (`after_save :send_email`)
- `rescue => e` without re-raise or log; `rescue Exception`
- `default_scope` — it leaks into every query, join and destroy
- `Model.all.each`, `.count` in a loop, `.map(&:id)` instead of `.pluck(:id)`, `.present?` on a relation (loads it — use `.exists?`)
- `puts`/`p` for diagnostics — `Rails.logger`
- Monkey patches of core classes or gems in `config/initializers`
- Editing `schema.rb` by hand, `rails db:reset` on a shared database, skipping `bundle exec`
- `Time.now`/`Date.today` — use `Time.current`/`Date.current` (time-zone aware)

# Guidelines: k6 / load testing

## Purpose

- A load test answers ONE stated question (capacity of a single server, regression against the last release, a comparison of two variants, behaviour under a burst) — write the question at the top of the script
- The result is data for a decision — every run is recorded, not watched and forgotten

## Synthetic data

- The synthetic data generator is PART of the solution (code in the repo), not an ad-hoc script
- Deterministic generation (seed) — the same seed = the same dataset
- Parameterised volume; scenarios reflect the real proportions of operations (read/write)
- Test users and payloads from `SharedArray` (loaded once, shared across VUs), not generated per iteration

## Scenarios

- Scripts in `load/` (`*.js` or `*.ts` — k6 runs TypeScript natively), versioned with the code, run by a task: `k6 run load/checkout.js`
- `export const options = { scenarios: {...}, thresholds: {...} }` — executors instead of bare `vus`/`duration`: `ramping-vus` for concurrency questions (closed model), `constant-arrival-rate` / `ramping-arrival-rate` for throughput questions (open model — the one that reveals a saturated server)
- Explicit phases: ramp-up → steady state → (optionally) stress; measure only the steady state (tag the stages, or run the steady state as its own scenario)
- `thresholds`: `http_req_duration: ['p(95)<300']`, `http_req_failed: ['rate<0.01']`, plus a `Rate` per business operation — the run turns green/red automatically, not "by eye"
- `check()` on every response (status + a field in the body) — a 200 with an error page counts as a failure
- Traffic through the public entry (reverse proxy / load balancer), not straight to the application container — you measure the system, not a fragment
- `sleep()` between iterations models think time; no `sleep` in an arrival-rate scenario

## Comparing variants (key)

- The implementations being compared MUST keep the same business semantics — the test measures an architectural difference, not accidentally different system behaviour
- Control the number of database queries in each variant — otherwise the result describes the number of calls, not the design
- One variable factor per experiment; identical data (the same seed) and an identical load profile
- A machine with dedicated CPU; the resource allocation of every component recorded with every run

## Measurement and results

- Measure with k6: latency (p50/p95/p99), throughput, errors; in parallel on the server side: CPU, RAM, IO and database metrics
- `handleSummary()` writes the JSON summary to a file (`perf-results/<date>-<commit>.json`) together with the conditions: commit, data seed, resource allocation, load profile — committed or kept as a CI artifact
- At least two runs per variant — a single measurement is an anecdote
- A warm-up run before the measured one when caches or JIT matter

## What to avoid

- Load testing on shared CPU cores (the neighbours' load lands on the measurement axis)
- Comparing runs with different data, volume or load profile
- Averaging everything — the answer is often in the latency tail (p99)
- Generating load from the same machine as the system during limit measurements (the k6 client competes for CPU) — always record where the load came from
- Fixed `vus` for a throughput question — a closed model slows down with the server and hides saturation
- Thresholds loose enough that nothing ever fails — a threshold that cannot turn red decides nothing
